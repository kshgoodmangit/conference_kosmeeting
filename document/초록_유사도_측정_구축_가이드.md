# 초록 유사도 측정 구축 가이드

## 1. 목적

사용자가 제출한 영문 초록을 기존에 등록된 초록과 비교하여 다음 정보를 관리자에게 제공한다.

- 가장 유사한 기존 초록 상위 5~10건
- 초록별 종합 유사도 점수
- 제목, Objective, Methods, Results, Conclusions 항목별 유사도 점수
- 가장 유사한 항목
- 두 초록의 원문 비교

유사도 점수는 표절률이나 복사율이 아니라 `BAAI/bge-small-en-v1.5` 모델이 계산한 의미적 유사도이다. 최종 판단은 관리자가 수행한다.

## 2. 전체 구성

```text
초록 등록 또는 수정
        ↓
Spring Boot가 Python 임베딩 API 호출
        ↓
BAAI/bge-small-en-v1.5가 항목별 384차원 벡터 생성
        ↓
Spring Boot가 float32 벡터를 BLOB으로 변환
        ↓
MariaDB abstract_embeddings 테이블에 저장
        ↓
기존 초록의 벡터와 코사인 유사도 계산
        ↓
유사 초록 상위 5~10건을 관리자 화면에 표시
```

구성 요소의 역할은 다음과 같다.

| 구성 요소 | 역할 |
|---|---|
| Python 임베딩 서버 | 영문 텍스트를 384차원 벡터로 변환 |
| Spring Boot | 임베딩 요청, 벡터 저장, 유사도 계산, API 제공 |
| MariaDB 10.6 | 초록 원문과 임베딩 BLOB 저장 |
| React 관리자 화면 | 유사 초록 목록과 항목별 점수 표시 |

## 3. 측정 대상과 단위 결정

현재 `abstract_submissions`의 다음 컬럼을 사용한다.

| 벡터 구분 | 원본 컬럼 | 최대 길이 |
|---|---|---:|
| `title` | `title` | 500자 |
| `objective` | `objectiveText` | 1,000자 |
| `methods` | `methodsText` | 1,000자 |
| `results` | `resultsText` | 1,000자 |
| `conclusions` | `conclusionsText` | 1,000자 |

전체 초록을 하나로 합쳐 모델에 전달하지 않고 각 항목을 별도로 변환한다. `BAAI/bge-small-en-v1.5`의 최대 입력 길이가 512토큰이므로 전체 초록을 한 번에 입력하면 뒷부분이 잘릴 수 있기 때문이다.

초록 하나당 기본적으로 5개의 벡터를 생성한다. 향후 벡터 DB 검색이나 전체 후보 검색이 필요하면 항목별 벡터의 가중 평균으로 `overall` 벡터를 추가할 수 있다.

## 4. Python 임베딩 서버 확인

임베딩 서버 프로젝트는 다음 위치에 별도로 구성한다.

```text
D:\dev\python\congress_embedding_service
```

기본 접속 주소는 다음과 같다.

```text
http://127.0.0.1:8001
```

### 4.1 상태 확인

```http
GET /health
```

예상 응답:

```json
{
  "status": "ok",
  "model": "BAAI/bge-small-en-v1.5",
  "dimension": 384
}
```

### 4.2 벡터 생성

```http
POST /embeddings
Content-Type: application/json
```

요청 예시:

```json
{
  "texts": [
    "Abstract title",
    "Objective contents",
    "Methods contents",
    "Results contents",
    "Conclusions contents"
  ]
}
```

응답 예시:

```json
{
  "model": "BAAI/bge-small-en-v1.5",
  "dimension": 384,
  "embeddings": [
    [0.0123, -0.0231, 0.0412],
    [0.0314, 0.0157, -0.0281]
  ]
}
```

실제 `embeddings`의 각 배열에는 384개의 값이 들어간다.

### 4.3 확인된 동작

- 5개 항목 요청 시 5개의 384차원 벡터 반환
- 모든 벡터의 L2 norm이 약 1.0으로 정규화됨
- NaN 또는 Infinity 값이 없음
- 약 4,000자 입력도 384차원 벡터로 정상 반환
- 빈 배열, 공백 문자열, null 입력은 HTTP 422로 거부

운영 서버에서는 모델 파일을 미리 다운로드하고 로컬 경로로 로드한다. 임베딩 서버는 `127.0.0.1`에만 바인딩하고 로그에 초록 원문을 기록하지 않는다.

## 5. 데이터베이스 변경

MariaDB 10.6은 네이티브 `VECTOR` 타입과 벡터 인덱스를 지원하지 않는다. 384개의 float32 값을 바이트 배열로 직렬화하여 `BLOB` 컬럼에 저장한다.

벡터 하나의 크기는 다음과 같다.

```text
384차원 × 4바이트 = 1,536바이트
```

300건의 초록에 항목별 벡터 5개를 저장할 경우 순수 벡터 용량은 약 2.3MB이다.

### 5.1 임베딩 테이블 생성

```sql
CREATE TABLE abstract_embeddings (
    seq BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '초록 임베딩 ID',
    abstractSeq BIGINT NOT NULL COMMENT '초록 접수 ID',
    sectionType VARCHAR(20) NOT NULL COMMENT
        '벡터 구분 (title/objective/methods/results/conclusions)',
    modelName VARCHAR(100) NOT NULL COMMENT '임베딩 모델명',
    modelRevision VARCHAR(100) NULL COMMENT '모델 버전 또는 리비전',
    dimension INT NOT NULL COMMENT '벡터 차원',
    embedding BLOB NOT NULL COMMENT 'Float32 임베딩 벡터',
    contentHash CHAR(64) NOT NULL COMMENT '전처리한 원문의 SHA-256',
    createdAt TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '생성일시',
    updatedAt TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP COMMENT '수정일시',
    UNIQUE KEY uk_abstract_embedding_section (abstractSeq, sectionType),
    INDEX idx_abstract_embedding_model (modelName),
    CONSTRAINT fk_abstract_embedding_abstract
        FOREIGN KEY (abstractSeq)
        REFERENCES abstract_submissions(seq)
        ON DELETE CASCADE
) COMMENT='초록 항목별 임베딩';
```

### 5.2 임베딩 처리 상태

비동기 처리를 적용하는 경우 초록별 처리 상태를 별도 테이블 또는 상태 컬럼으로 관리한다.

```text
pending     생성 대기
processing  생성 중
complete    생성 완료
failed      생성 실패
```

실패 사유와 마지막 시도 시간을 함께 기록하여 재처리할 수 있어야 한다.

클라이언트가 검증해야 할 사항:

1. 요청한 텍스트 수와 반환된 벡터 수가 같은지 확인한다.
2. 응답의 `dimension`이 384인지 확인한다.
3. 각 벡터의 실제 배열 길이가 384인지 확인한다.
4. NaN 또는 Infinity가 포함되면 저장하지 않는다.
5. 연결 실패와 타임아웃을 구분하여 처리한다.
6. 요청 또는 오류 로그에 초록 원문 전체를 남기지 않는다.

## 8. 텍스트 전처리와 변경 감지

모델에 전달하기 전 다음 처리만 적용한다.

- 앞뒤 공백 제거
- CRLF와 LF 줄바꿈 통일
- 불필요한 연속 공백 정리
- 빈 항목 제외

다음 내용은 제거하거나 임의로 변경하지 않는다.

- 영문 대소문자
- 구두점
- 숫자
- 의학·과학 용어
- 단위와 기호

전처리한 텍스트의 SHA-256을 계산하여 `contentHash`에 저장한다.

```text
contentHash 동일 → 기존 벡터 재사용
contentHash 변경 → 해당 항목만 다시 생성
```

## 9. 벡터 BLOB 변환 구현

Python 응답의 숫자 배열을 Java의 `float[]`로 변환한 후 `byte[]`로 직렬화한다.

권장 파일:

```text
service/EmbeddingBinaryConverter.java
```

```java
public static byte[] toBytes(float[] vector) {
    ByteBuffer buffer = ByteBuffer
            .allocate(vector.length * Float.BYTES)
            .order(ByteOrder.LITTLE_ENDIAN);

    for (float value : vector) {
        buffer.putFloat(value);
    }

    return buffer.array();
}

public static float[] fromBytes(byte[] bytes) {
    if (bytes.length % Float.BYTES != 0) {
        throw new IllegalArgumentException("Invalid embedding byte length.");
    }

    ByteBuffer buffer = ByteBuffer
            .wrap(bytes)
            .order(ByteOrder.LITTLE_ENDIAN);

    float[] vector = new float[bytes.length / Float.BYTES];
    for (int i = 0; i < vector.length; i++) {
        vector[i] = buffer.getFloat();
    }

    return vector;
}
```

저장과 조회에서 동일한 byte order를 사용해야 한다.

## 11. 초록 등록·수정과 연결

현재 관리자 초록 API의 저장 성공 이후 임베딩 생성을 요청한다.

```text
POST /api/admin/abstracts
PUT  /api/admin/abstracts/{seq}
```

권장 처리 순서:

```text
초록 저장 트랜잭션 커밋
        ↓
임베딩 생성 이벤트 발행
        ↓
비동기 임베딩 생성
        ↓
성공 시 complete, 실패 시 failed
```

Python 임베딩 서버가 중단되어도 초록 등록 자체는 성공해야 한다. 임베딩 실패는 별도로 기록하고 관리자 재계산 또는 자동 재시도가 가능해야 한다.

간단한 초기 구현은 `@TransactionalEventListener`의 `AFTER_COMMIT`과 `@Async`를 사용할 수 있다. 운영 안정성을 높이려면 DB 기반 작업 큐와 `@Scheduled` 재시도를 사용한다.

## 12. 코사인 유사도 계산

정규화된 벡터끼리는 내적 결과가 코사인 유사도와 같다.

```java
public static double cosineSimilarity(float[] a, float[] b) {
    if (a.length != b.length) {
        throw new IllegalArgumentException("Embedding dimensions do not match.");
    }

    double dot = 0.0;
    double normA = 0.0;
    double normB = 0.0;

    for (int i = 0; i < a.length; i++) {
        dot += a[i] * b[i];
        normA += a[i] * a[i];
        normB += b[i] * b[i];
    }

    if (normA == 0.0 || normB == 0.0) {
        return 0.0;
    }

    return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

비교 대상 조건:

- 현재 초록 자신은 제외
- `draft` 상태는 제외
- 동일한 모델과 동일한 차원의 벡터만 비교
- 삭제된 초록은 제외

300건 규모에서는 모든 기존 초록과 정확 비교해도 충분하다. 별도 벡터 DB는 필요하지 않다.

## 13. 종합 점수 계산

항목별 코사인 유사도를 계산하고 가중 평균으로 종합 점수를 만든다.

초기 가중치 예시:

```text
title        10%
objective    20%
methods      20%
results      30%
conclusions  20%
```

```java
double overallSimilarity =
        titleSimilarity * 0.10
      + objectiveSimilarity * 0.20
      + methodsSimilarity * 0.20
      + resultsSimilarity * 0.30
      + conclusionsSimilarity * 0.20;
```

비어 있는 항목은 계산에서 제외하고 남은 항목의 가중치 합이 1이 되도록 재계산한다. 종합 점수와 함께 가장 높은 항목 점수를 반드시 반환한다. 특정 항목만 복사된 경우 종합 점수가 낮아질 수 있기 때문이다.

## 14. 유사도 점수 해석

코사인 유사도 `0.4553`을 숫자로 표현하면 45.53점이지만 내용의 45.53%가 동일하다는 의미는 아니다. 코사인 유사도는 확률이나 표절률이 아니라 벡터 방향의 가까움을 나타낸다.

관리자 화면에서는 다음 명칭을 사용한다.

```text
AI 의미 유사도
모델 유사도 점수
유사 초록 검토 필요
```

다음 명칭은 사용하지 않는다.

```text
표절률
복사율
내용 일치율
```

초기 표시 기준 예시:

| 코사인 점수 | 화면 표시 | 의미 |
|---:|---|---|
| 0.90 이상 | 매우 높음 | 우선 검토 |
| 0.80 이상 0.90 미만 | 높음 | 검토 권장 |
| 0.70 이상 0.80 미만 | 보통 | 참고 |
| 0.70 미만 | 기본 목록에서 숨김 | 낮은 유사도 |

이 기준은 고정된 표준이 아니다. 실제 등록 초록과 중복 표본을 이용해 보정해야 한다.

## 16. 기존 초록 일괄 벡터 생성

기존 초록에는 임베딩이 없으므로 최초 한 번 배치 처리가 필요하다.

처리 순서:

1. `draft`가 아닌 기존 초록을 조회한다.
2. 모델과 contentHash가 같은 기존 임베딩은 건너뛴다.
3. 초록의 5개 항목을 배치 요청한다.
4. 벡터를 검증하고 BLOB으로 저장한다.
5. 성공, 건너뜀, 실패 건수를 기록한다.
6. 실패한 초록만 다시 처리한다.

Python 모델은 서버 시작 시 한 번만 로드하며 초록마다 다시 로드하지 않는다. 초기 배치는 관리자 전용 실행 기능이나 별도 명령으로 제공하고 애플리케이션이 시작될 때마다 자동 실행하지 않는다.

- 두 초록 원문 비교 버튼

화면 예시:

```text
유사 초록 분석                                      [다시 계산]

매우 높은 유사도 1건 · 높은 유사도 2건

1. ABS-2026-0128                                     91.3점
   Effects of Exercise on Cardiovascular Health
   Results 96.8 · Methods 91.4                       [비교]

2. ABS-2026-0052                                     83.7점
   Cardiovascular Health in Adults
   Methods 89.2                                      [비교]
```

성공, 오류, 안내 메시지는 공통 `NotificationToast`를 사용한다. 재계산 확인이 필요하면 공통 `ConfirmDialog`와 `useConfirm()`을 사용한다.

## 18. 정확도 보정

운영 전 다음 검증용 초록을 준비한다.

1. 완전히 동일한 초록
2. 일부 단어와 문장 순서만 변경한 초록
3. Objective만 유사한 초록
4. Methods만 복사한 초록
5. Results만 복사한 초록
6. 같은 연구 분야지만 서로 다른 연구
7. 전혀 다른 연구 분야의 초록

각 유형의 점수 분포를 확인하여 화면 표시 기준을 확정한다. 같은 연구 분야의 정상적인 초록이 과도하게 경고되지 않는지 반드시 확인한다.

문장 단위 복사 탐지가 중요하면 다음 단계에서 영문 word 또는 character n-gram 유사도를 함께 계산한다. BGE 점수는 의미 유사성을 찾고 n-gram 점수는 실제 문구 재사용을 보완한다.

## 20. 운영 점검

- Python 임베딩 서버가 Spring Boot와 같은 서버에서 실행되는지 확인한다.
- 임베딩 서버가 `127.0.0.1`에만 바인딩되는지 확인한다.
- 모델을 운영 중 외부에서 다운로드하지 않도록 로컬 모델 경로를 사용한다.
- 서비스 시작 시 `/health` 상태를 확인한다.
- 로그에 초록 제목이나 본문 전체를 기록하지 않는다.
- 모델명과 리비전을 임베딩 데이터에 기록한다.
- 모델을 변경하면 기존 벡터를 모두 재생성한다.
- 임베딩 데이터는 원문으로부터 다시 만들 수 있으므로 복구 절차를 문서화한다.
- Python 서버 장애가 초록 접수 기능을 중단시키지 않도록 한다.
