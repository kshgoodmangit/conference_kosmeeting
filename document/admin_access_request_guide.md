# 관리자 접근 허용 요청

## 적용 순서

1. 배포 대상 DB를 확인하고 `document/admin_access_request_migration.sql`을 MariaDB 10.6에서 **1회 수동 실행**합니다. 접수·잠금·메일 작업 테이블 3개와 시스템관리 하위 `접근허용요청` 메뉴를 추가합니다. 애플리케이션은 스키마를 자동 변경하지 않습니다.
2. 기존 유지보수 메일 설정(`app.maintenance-mail`)과 발송 계정의 SMTP 인증을 확인하고, 활성 상태의 `maintenance` 권한 관리자에게 **연락 이메일(contactEmail)**을 등록합니다. 로그인 ID가 아닌 연락 이메일을 수신 주소로 사용합니다. 중복 수신 주소는 한 번만 발송합니다.
3. 새 백엔드·프론트엔드를 배포/재시작합니다. 접근 허용 요청은 항상 사용하는 기능으로, 별도의 활성화 또는 사이트 URL 환경변수가 필요하지 않습니다. 기존에 추가했던 두 환경변수는 삭제해도 됩니다. DB 스키마는 서버 재시작 전에 적용해야 합니다.
4. 시스템관리 하위 메뉴와 유지보수 계정의 실제 메일 수신을 점검합니다. 이 SQL은 공통 관리자 `system` 메뉴가 존재하는 것을 전제로 합니다.

`DB_ENC_STRING`은 기존 개인정보 암호화 키를 그대로 사용합니다. 키를 변경하면 기존 요청과 수신 이메일 복호화가 되지 않습니다. 비밀값을 소스에 추가하지 않습니다.

## 동작

- 로그인 화면의 요청 모달: 도메인·요청 IP는 서버 확인값을 표시하고, 소속·이름·전화번호·목적·사용 시작일/종료일을 입력합니다. CAPTCHA는 사용하지 않습니다.
- 도메인·포트·프로토콜은 서버가 수신한 HTTP 요청에서 확인하여 접수 시 저장합니다. 메일 링크도 이 저장값을 사용합니다. 개발 프록시는 원래 Host를 보존하므로 `localhost:5173`으로 접속하면 해당 주소가 표시됩니다. 별칭 도메인은 별도 사이트로 구분되며 목록·승인도 현재 접속 주소의 요청만 처리합니다.
- `Origin`·`Referer`·폼에 들어온 사이트 주소를 메일 링크로 사용하지 않습니다. URL은 HTTP/HTTPS, 올바른 호스트·포트만 허용하고 사용자정보·경로·쿼리·프래그먼트·복수 Host는 거부합니다. 기본 포트 80/443은 생략합니다.
- 리버스 프록시 뒤에서는 기존 `app.admin-ip-access.trusted-proxies`에 등록된 프록시의 `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`만 반영합니다. 프록시는 이 헤더를 외부 입력 그대로 전달하거나 누적하지 말고 검증된 단일 값으로 덮어써야 합니다. 해당 헤더가 없으면 원래 Host를 보존하고 실제 외부 프로토콜이 서버에 전달되도록 구성합니다.
- **운영 웹서버/프록시는 서비스에 등록되지 않은 Host를 거부하고 백엔드 직접 접근을 제한해야 합니다.** URL 문법 검사만으로 도메인 소유권을 확인할 수는 없습니다. 임의 Host를 허용하면 잘못된 사이트의 메일 링크가 생성되거나 도메인을 바꿔 사이트별 접수 제한을 우회할 수 있습니다.
- IP는 기존 `ClientIpResolver`를 재사용합니다. 리버스 프록시 환경에서는 `app.admin-ip-access.trusted-proxies`에 실제 신뢰 프록시만 설정해야 합니다. 신뢰되지 않은 연결의 `X-Forwarded-For`는 무시합니다.
- 동일 사이트·정규화된 IP의 유효한 대기 요청이 있으면 새 요청과 메일을 만들지 않습니다. DB 행 잠금으로 동시 요청도 직렬화합니다.
- IP별 접수 제한은 10분 간격, 하루 3건입니다. 접수 성공 이력 기준이며 날짜는 서버 Clock(Asia/Seoul) 기준입니다. 사이트 전체 시간당/일일 발송 상한은 없습니다.
- 대기 요청은 접수 24시간 경과 또는 요청 사용 종료일 경과 시 만료됩니다. 목록에서 만료로 표시하고 더 이상 승인할 수 없습니다. 새 요청에도 기존 IP별 제한이 적용됩니다.
- 개인정보(소속·이름·연락처·목적)와 메일 수신 주소는 기존 DB 암호화 방식으로 저장합니다. IP·접속 사이트 주소·처리상태는 조회와 제한을 위해 평문으로 저장합니다.

## 메일 및 처리

- 접수와 수신자별 메일 작업을 하나의 DB 트랜잭션으로 저장합니다. SMTP 장애로 접수 자체가 사라지지 않습니다.
- 30초 간격으로 발송 대기를 확인합니다. 실패 시 5분 간격으로 **최대 3회 시도(첫 발송 포함)**합니다. 메일 전송 직후 프로세스가 중단되는 예외 상황에서는 재시도로 같은 메일이 다시 수신될 수 있습니다.
- 관리자 요청 목록의 도메인은 링크 없이 텍스트로 표시합니다. 메일의 도메인 링크는 요청 사이트 기본 주소로, ‘관리자 바로가기’ 링크는 해당 사이트의 관리자 진입 주소(`/admin`)로 이동합니다. 로그인 후 시스템관리 → 접근허용요청에서 내역을 확인합니다. 이메일 링크 자체는 승인하지 않습니다.
- 목록은 검색·상태 필터·서버 집계 통계·페이지 이동·상세보기·메일 상태를 제공합니다. 수신 대상이 없으면 `수신자 없음`, 최종 실패 시 `발송 실패`로 표시합니다. 이미 저장된 메일 수신자 목록은 이후 계정 변경으로 자동 재생성되지 않습니다.
- 기능 → 접근허용 → 공통 확인창 → 요청 IP와 사용기간을 기존 접근허용 IP 테이블에 즉시 등록하고 상태를 허용으로 변경합니다. **기존 IP 허용 규칙과 동일하게 서버 전체에 적용**하며 특정 학회에만 한정하지 않습니다.
- 동일 IP의 활성 규칙이 이미 전체 요청 기간을 허용하면 재사용합니다. 비활성 또는 기간 충돌 규칙은 덮어쓰지 않고 기존 접근허용 IP 메뉴에서 확인하도록 안내합니다.
- 거절 시 IP를 등록하지 않고 처리자·처리시각을 기록합니다. 처리된 요청은 다시 승인/거절할 수 없습니다(동일 승인 재호출은 중복 등록 없이 성공).
- 요청 정보/접수 API만 IP 제한 예외입니다. 목록·승인·거절은 기존 관리자 권한·접속 IP 검사를 유지하고, 모든 POST는 기존 CSRF 검증을 유지합니다.

## 검증 및 운영 주의

- 단위 테스트는 DB·SMTP를 mock으로 대체합니다. 실제 DB 스키마 적용, 다중 연결 잠금 검증, 실제 메일 수신은 별도 배포 점검이 필요합니다.
- UI는 가상 데이터로 목록·확인창·승인 후 통계 갱신·필수값 오류를 확인했습니다. 내장 브라우저의 날짜 선택기 오류로 날짜 입력을 포함한 접수 완료까지의 브라우저 검증은 마치지 못했으므로 일반 브라우저에서도 점검해야 합니다.
- CAPTCHA와 사이트 전체 발송 상한이 없으므로 여러 IP를 동원한 분산 요청까지 방지하지는 않습니다. 프록시의 비정상 트래픽 차단과 개인정보 보관/파기 정책을 운영 환경에 맞게 관리해야 합니다.
- 로컬 Vite 프록시는 백엔드가 루프백 IP를 볼 수 있습니다. 실제 사용자 IP 검증은 운영 프록시 설정과 함께 확인합니다.
