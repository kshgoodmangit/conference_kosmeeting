# 관리자 비밀번호 5회 실패 잠금

## 동작

- 관리자 로그인(`/api/admin/login`)에서 계정별 비밀번호 연속 실패를 기록합니다.
- 같은 계정을 사용하는 캐시 복구 인증(`/api/admin/cache/reload`)도 동일한 실패 횟수와 잠금 상태를 사용합니다.
- 캐시 복구 API에도 공통 접근허용 IP 검사를 적용합니다. `app.admin-ip-access.enabled=true`일 때 비허용 IP는 비밀번호 검사 전에 403으로 차단되어 로그인 실패 횟수가 증가하지 않습니다. 허용 IP에서도 관리자 비밀번호와 CSRF 토큰이 필요합니다.
- 5번째 실패부터 로그인할 수 없습니다. 올바른 비밀번호를 입력해도 거부하며 자동 해제하지 않습니다.
- 로그인 화면은 3번째 실패 시 "2회 더 실패하면 계정이 잠깁니다", 4번째 실패 시 "1회 더 실패하면 계정이 잠깁니다"를 안내합니다.
- 잠금 전 정상 인증에 성공하면 연속 실패 횟수를 0으로 초기화합니다.
- 잠금 중 추가 시도는 비밀번호 검증과 실패 기록 갱신을 하지 않습니다.
- 관리자 계정 관리의 기존 비밀번호 초기화 기능을 다른 관리자가 실행하면 새 임시 비밀번호로 교체하면서 잠금을 해제합니다.
- 본인 계정에 대한 관리자 비밀번호 초기화 API 호출은 403으로 거부합니다. 본인 비밀번호 변경 기능은 잠금을 해제하지 않습니다.
- 관리자 로그인 경로를 공유하는 admin, maintenance, reviewer 계정에 적용됩니다. 캐시 복구는 기존대로 admin/maintenance만 허용합니다.
- 기존 로그인 세션을 강제 종료하는 기능은 포함하지 않습니다. 이 잠금은 새로운 비밀번호 인증을 차단합니다.

## 적용 순서

1. `admin_accounts`가 InnoDB인지 확인하고 DB를 백업합니다.
2. `document/admin_login_lockout_migration.sql`을 대상 DB에 1회 적용합니다.
3. 애플리케이션을 배포합니다. SQL이 적용되지 않으면 관리자 조회가 실패하므로 반드시 먼저 적용합니다.
4. 테스트 계정으로 4회 실패 후 정상 인증, 5회 실패 후 로그인 거부, 다른 관리자 초기화 후 재로그인을 확인합니다.

SQL은 애플리케이션 시작 시 자동 실행하지 않습니다. 개발 DB와 운영 DB에 각각 적용해야 합니다.
모든 관리자 계정이 잠긴 경우를 대비하여 별도 관리자 계정 및 운영 복구 절차를 마련합니다.

캐시 복구의 IP 검사는 현재 메모리에 적재된 허용목록을 사용합니다. 허용목록 캐시가 비었거나 허용 IP가 모두 만료된 경우 웹 캐시 복구도 차단됩니다. 이때는 승인된 서버 운영 절차로 DB 허용목록과 기간을 확인·복구한 후 애플리케이션을 재시작하여 캐시를 다시 적재합니다. 프록시를 사용하는 운영 환경에서는 신뢰할 프록시만 `trusted-proxies`에 등록하고 원래 클라이언트 IP가 전달되도록 구성합니다.

## 구현

- `AdminCredentialVerifier`가 별도 트랜잭션에서 계정을 `SELECT ... FOR UPDATE`로 조회하고 검증·횟수 갱신을 처리합니다.
- 인증 거부 예외는 실패 기록을 커밋합니다. DB 오류 등 다른 예외는 롤백하며 인증에 성공한 것으로 처리하지 않습니다.
- 계정 단위 DB 행 잠금으로 여러 요청/서버의 실패 횟수를 직렬화합니다. InnoDB의 `FOR UPDATE`는 트랜잭션 안에서 사용해야 합니다. [MariaDB 공식 문서](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update)
- 상태는 `loginFailureCount`, `loginLockedAt`에 저장하여 서버 재시작 후에도 유지합니다.
- 비밀번호 초기화는 비밀번호 교체와 실패 횟수·잠금 초기화를 한 UPDATE에서 처리합니다.

이 작업은 보안 점검 F04의 계정별 로그인 실패 제한을 보완합니다. IP별 요청 제한, MFA, 로그인 실패 이벤트 감사는 별도 과제입니다.
