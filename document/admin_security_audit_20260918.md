# 관리자 보안 점검 결과 — 2026-09-18

> 후속 조치: 캐시 복구 API의 `@IpAccessExempt`를 제거해 공통 접근허용 IP 검사를 적용했다. IP 제한이 활성화된 환경에서 비허용 IP는 인증 검증 전에 403으로 차단되며 계정 실패 횟수에 영향을 주지 않는다. 허용 IP의 관리자 비밀번호 인증·CSRF 검사는 유지한다. 아래 점검 결과는 수정 전 기록이다. 기존 세션 회수 누락과 허용 IP에서의 계정 잠금 정책은 이번 변경 범위에 포함하지 않았다. 실행 중인 서버에는 재시작 또는 재배포 후 반영된다.

## 결론

`http://localhost:5173/admin` 및 연결된 `localhost:8080`을 점검했다. 이번에 수행한 비로그인 요청에서는 관리자 로그인 우회나 관리자 데이터 열람을 재현하지 못했다. 다만 현재 소스의 인증·세션 로직을 모의 계정으로 실행한 격리 테스트에서 아래 두 문제를 재현했다.

| 우선순위 | 문제 | 재현 방식 | 전제 조건 |
| --- | --- | --- | --- |
| 높음 / P1 | 계정 정지·삭제·비밀번호 변경 후 기존 관리자 세션 유지 | 실제 서비스·인터셉터를 사용하는 모의 저장소 테스트 4건 | 이전에 발급된 유효한 관리자 세션 보유 |
| 중간 / P2 | 공개 캐시 복구 API를 통한 관리자 계정 잠금 | 실제 컨트롤러·인증 검증기와 모의 저장소 테스트 1건 | 유효한 관리자 아이디를 알고 복구 API에 접근 가능 |

실제 계정을 정지·삭제·잠그거나 실제 비밀번호를 변경하지 않았다. 애플리케이션 소스는 수정하지 않았으며 점검 스크립트·격리 테스트·이 보고서만 추가했다. 실패한 로그인 시도는 빈 아이디와 SQL 구문 형태의 점검 입력만 사용했다. HTTP 응답 본문, 쿠키 값, CSRF 토큰, 개인정보를 증거 파일에 저장하지 않았다.

## 1. 기존 관리자 세션이 계정·비밀번호 변경을 반영하지 않음

### 근거

- `src/main/java/com/bjworld21/congress/config/AdminSessionInterceptor.java:20`: 세션의 `adminSeq` 존재 여부와 저장된 `adminRole`만 검사한다. 현재 계정 상태, 계정 존재 여부, 자격 증명 변경 여부를 확인하지 않는다.
- `src/main/java/com/bjworld21/congress/service/AdminService.java:327`: 계정 상태·역할 변경 시 기존 세션을 폐기하지 않는다.
- 같은 파일 `:402`, `:434`, `:541`: 삭제·비밀번호 초기화·본인 비밀번호 변경도 다른 기존 세션을 폐기하지 않는다.
- `src/main/java/com/bjworld21/congress/controller/AdminSelfController.java:34`: 비밀번호를 변경한 요청의 세션만 무효화한다.
- `src/main/java/com/bjworld21/congress/controller/AdminController.java:147`: `/api/admin/session`은 계정 상태와 역할을 다시 읽지만 모든 관리자 API 요청에 강제되는 검사가 아니다. 비밀번호가 바뀌었는지도 검사하지 않는다.

### 재현 결과

네트워크와 실제 DB에 연결하지 않는 테스트에서 기존 로그인 세션을 만든 뒤 실제 서비스 메서드로 모의 계정을 변경했다.

1. 계정을 `inactive`로 변경한 후에도 기존 세션이 관리자 인터셉터를 통과했다.
2. 모의 저장소에서 계정을 삭제한 후에도 기존 세션이 통과했다.
3. 비밀번호 초기화 후 기존 세션으로 `/api/admin/session`의 실제 컨트롤러 메서드를 호출해도 200이 반환됐고 관리자 인터셉터도 통과했다.
4. 본인 비밀번호 변경 시 호출한 세션은 무효화됐지만, 동일 계정의 별도 기존 세션은 계속 통과했다.

역할 하향 조정에도 저장된 역할이 남는 동일한 문제가 코드상 존재한다. 이번 추가 테스트에서는 역할 변경 자체를 별도로 재현하지 않았다.

### 영향과 수정 방향

세션이 탈취됐거나 접근 권한을 회수해야 하는 상황에서 계정 정지·삭제·비밀번호 변경만으로 접근을 확실히 끊을 수 없다. 공격자는 세션 확인 API를 생략하고 보호 API를 직접 호출할 수 있다. 현재의 60분 세션 타임아웃은 유휴 시간 기준이므로 적극적으로 요청하는 세션의 즉시 회수 수단이 아니다.

모든 보호 요청에서 현재 계정 존재 여부·활성 상태·역할·자격 증명 버전을 검증하고, 상태·역할·비밀번호 변경 및 삭제 시 기존 세션을 무효화해야 한다. 관리자·심사자·유지보수·본인 계정 API에 동일한 원칙을 적용한다. 로그인 시 저장한 `authVersion`과 서버의 현재 버전을 비교하거나 서버 측 세션 레지스트리로 계정의 세션을 회수할 수 있다. 일반 회원에는 이미 자격 증명 지문 검사(`MemberCredentialSessionConfig`)가 있으므로 공통화도 검토할 수 있다.

## 2. 공개 복구 API에서 실패 5회로 정상 관리자 로그인을 잠글 수 있음

### 근거

- `src/main/java/com/bjworld21/congress/config/ConferenceAdminWebMvcConfig.java:44`: `/api/admin/cache/reload`은 관리자 세션 검사 예외다.
- `src/main/java/com/bjworld21/congress/controller/AdminCacheRecoveryController.java:38`: 같은 API가 `@IpAccessExempt`로 IP 제한에서도 제외된다.
- 같은 파일 `:43`: `verifyActiveAdministrator`를 호출한다.
- `src/main/java/com/bjworld21/congress/service/AdminCredentialVerifier.java:39`: 복구 인증과 로그인은 동일한 검증 로직과 계정 실패 횟수를 공유한다.
- 같은 파일 `:59`, `:64`: 5회 실패하면 올바른 비밀번호를 입력해도 거절한다. 자동 해제 시간 검사가 없고 다른 관리자의 초기화가 필요하다.
- CSRF 토큰 발급 API는 비로그인 사용자에게도 제공된다. CSRF 방어는 공격자가 자신의 세션으로 요청하는 계정 잠금 시도를 막지 않는다.

### 재현 결과

모의 계정에 대해 실제 `AdminCacheRecoveryController`와 `AdminCredentialVerifier`를 실행했다. 잘못된 비밀번호로 복구 인증을 5회 호출하자 실패 횟수가 5가 됐고, 이후 올바른 비밀번호를 주어도 로그인 검증기가 비밀번호 비교 전에 거절했다. 캐시 재로드 자체는 실행되지 않았다.

실행 중인 서버에는 빈 자격 증명으로 1회 요청해 401을 확인했으며, 실제 계정에 대한 5회 실패 요청은 보내지 않았다. 외부망에서 이 로컬 서버에 접근할 수 있는지는 검사하지 않았다.

### 영향과 수정 방향

복구 API에 접근 가능하고 관리자 아이디를 아는 사람이 정상 관리자의 신규 로그인을 차단할 수 있다. 이 경로는 애플리케이션 IP 제한의 예외라 일반 로그인 화면의 IP 제한만으로 방어되지 않는다. 여러 관리자가 잠기면 복구 절차에도 영향을 줄 수 있다.

복구 경로에 별도 인증 요소나 제한된 복구 채널을 적용하고, 계정·요청 출처별 속도 제한과 점진적 지연, 시간 제한 잠금 및 감사 알림을 설계해야 한다. 비밀번호 대입 방어를 유지하면서 비인증 요청 몇 번만으로 무기한 업무 차단이 되지 않도록 한다. 운영 프록시의 추가 제한 여부는 이번 점검 범위 밖이다.

## 실제 HTTP 점검 결과

총 39건을 낮은 빈도로 요청했다. 브라우저에는 관리자 로그인 폼이 표시됐으며 기존 로그인 쿠키를 사용하지 않았다.

| 항목 | 결과 |
| --- | --- |
| 5173·8080의 관리자 계정·회원·초록·학회 설정·IP 허용목록·메일 목록 API | 인증 없이 401 |
| 관리자 세션·심사자 프로필·유지보수 API | 인증 없이 401 |
| `/admin` HTML | 200, 로그인 화면을 제공하는 정상 동작 |
| `/api/admin/menu-settings`의 GET | 405, 실제 트리 조회 경로와 다르므로 접근통제 통과 근거에서 제외 |
| 중복 슬래시·세미콜론·인코딩 등 경로 변형 8종 | 400 또는 401 |
| 가짜 JSESSIONID·관리자 역할/번호 헤더·Bearer 토큰·X-Forwarded-For | 관리자 API 401 |
| CSRF 없는 로그인 POST | 403 및 `X-CSRF-ERROR: true` |
| 익명 세션에서 정상 CSRF를 받은 뒤 관리자 계정 생성 API에 빈 요청 | 401, 생성 미실행 |
| 빈 자격 증명·SQL 구문 형태 아이디로 로그인 시도 | 401 |
| 캐시 복구 API의 빈 자격 증명 | 401 |
| 업로드 이미지 경로의 인코딩된 상위 경로 접근 | 400 |
| 외부 Origin으로 관리자 API 호출 | 401. `Access-Control-Allow-Origin: *`가 있으나 credentials 허용 헤더는 없어 이것만으로 인증 데이터 유출이라고 판단하지 않음 |

로컬 HTTP에서 세션 쿠키는 `HttpOnly`였고 `Secure`, 명시적인 `SameSite`는 없었다. 8080 응답에는 `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`가 있었으며 5173의 개발 서버 HTML은 다르다. 이는 관찰 사항이며 운영 HTTPS·프록시 설정까지 확인한 취약점 판정은 아니다.

## 이번 점검의 한계
