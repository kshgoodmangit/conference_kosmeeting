- `AdminOperationStatusPage.tsx`: 고정된 가상 데이터, 2026-09-13 14:30 KST. 실제 감시·알림·백업·PG 요청 없음.
- 메뉴 키 `dashboard-operation-status`는 DB `menu_settings`에 정식 등록됨(seq 82). 부모 dashboard, 순서 40, 사용/노출/로그인 필요 활성화. 프론트엔드 강제 추가와 직접 경로 fallback 제거. 지원 메뉴·화면 렌더링·아이콘 연결 유지.
- 등록 실적·미납 독촉·심사 일정은 제외하고 이용 장애와 장애 예방, 데이터 보호를 표시한다.

## 실제 구현 방향

현재 화면의 모든 값은 예시다. 아래 수집 기능은 구현 범위 제안이며 구현 완료를 의미하지 않는다.

| 항목 | 수집 방식 및 제한 |
|---|---|
| 외부 홈페이지 접속 | 별도 감시 프로세스가 사전에 등록된 공개 URL의 HTTP 응답 및 기대 콘텐츠를 1분 간격 점검. SSRF 방지를 위해 임의 URL 입력 금지. 자체 서버 내부 점검만으로 외부 접속 정상 판정 금지 |
| 최근 서버 오류 | 요청 필터 또는 접근 로그에서 5xx / 전체 요청 집계. 요청 시각·정규화된 경로·추적 ID 기록. 비밀번호, 토큰, 개인정보, 요청 본문 수집 금지. 예시 18/6000 = 0.3%. 업로드 저장 실패 3건은 여기에 포함되며 나머지 15건의 원인은 이 화면에서 단정하지 않음 |
| 저장소 | UploadStorage 및 UploadProperties 기준 경로에서 Java FileStore 전체/가용 용량 조회. 네트워크 저장소나 권한 문제로 조회 불가능하면 미확인. 볼륨 전체 사용량은 학회 사용량과 구분. 예시 100 GB 중 85 GB 사용 |
| DB 상태 | 제한 시간 내 연결 및 기본 조회 성공 확인. 읽기 성공이 모든 쓰기 트랜잭션의 정상 동작을 보장하지 않음 |
| 업로드 저장 실패 | 저장 단계 실패를 별도 계측. 형식·용량 검증 거절과 구분. 시도 120건 중 실패 3건. 실패와 저장소 용량 경고의 인과관계는 조사 전 단정 금지 |
| 메일 지연 | 영속 발송 대기열의 상태와 대기 시작 시각 필요. 현재 MailSendJob / MailCampaignRecipient 엔티티는 seq만 있어 실제 발송 큐·전송 결과 수집 구현을 먼저 확인/보강해야 함. 예시 대기 10분 초과 6건, 최장 18분. 접수확인 메일에 동일 계측 적용 필요 |
| 결제 불일치 | PG의 서버 승인 조회 결과와 내부 등록 상태 대조. 승인 요청/검증 이력 저장과 provider별 조회 지원 필요. 단순 미납 건수를 불일치로 취급하지 않음. 해당 비교 검증 기능이 없으면 미수집 표시 |
| 인증서 | 공개 도메인의 실제 제공 TLS 인증서 만료 시각 점검. CDN/프록시에서 제공되는 인증서 기준. 예시 만료일 2026-10-01 14:30 KST, 기준 시각 대비 18일 |
| 백업·복구 | 외부 백업 작업 결과를 DB/첨부파일 각각 수집. 시작·종료·대상·성공·실패·보관 위치 및 복구 시험 결과를 별도 기록. 현재 미수집 예시이며 자동 백업이 있다고 가정하지 않음 |
| 장애 알림 | 담당자/수신 경로 설정, 시험 알림 성공과 실제 장애 통보 기록 수집. 홈페이지와 독립된 감시·알림 경로 필요 |

## 운영 계약

- 업무별 로그/메일/결제는 선택 학회 범위, 공용 DB·저장소는 서버 공용 범위를 명시한다. 관리자 인증 및 권한을 서버에서 검증한다.
- 각 점검에 checkedAt / observedWindow / status / source를 저장한다. 갱신 지연과 미수집, 조회 실패를 정상 및 0건과 구분한다. 오래된 정상 결과는 현재 정상으로 재사용하지 않는다.
- 예시 임계값: 오류율 0.1% 이상, 저장소 사용률 80% 이상, 인증서 만료 30일 이내. 운영 규모에 맞춰 변경하며 최소 요청수·연속 실패·회복 조건으로 알림 과다 발생을 방지한다.
- 공개 접속 60/60 성공은 최근 1시간의 60회 점검에 대한 결과이며 전체 API 성공률이나 월간 가동률이 아니다.
- 전체 상태를 평균으로 계산하지 않는다. 이용 장애와 미확인 데이터 보호 항목을 별도로 강조한다.
- 실제 연동 시 조회 중·실패는 공통 토스트와 상태 안내를 사용하고 요청 취소/중복 조회 방지 및 갱신 중 정리를 적용한다.

## 개인정보 현황 화면 (백엔드 작업 없음)

- 개인정보 보유 현황: 회원 1,240 + 등록 860 + 저자 260 + 주소록 120 = 2,480 레코드. 사람 수가 아니며 메뉴 간 중복 포함. 첨부파일 본문은 제외한다.
- 기간별 추출 성공 횟수/추출 행 수/조회 횟수는 가상 관리자 5계정 데이터에서 합산한다. 오늘/최근 7일 전환은 세 지표 및 관리자 표에 적용하고 현재 보유 현황은 고정한다.
- 다운로드 횟수, 추출 행 수, 조회 횟수 내림차순 정렬을 제공한다. 관리자 이름은 가상 마스킹 이름과 구분 가능한 예시 계정으로 표시한다.
- 오늘 확인 대상 안내는 기간 필터와 무관한 오늘 기준임을 명시한다. 일 5회 또는 1,000행 기준은 화면 검토용 가정이며 법적 기준이나 오남용 판정이 아니다.
- ExcelDownloadLog는 status, rowCount, adminSeq, reason, completedAt을 보유해 성공 횟수와 행 수 집계에 활용 가능하다. 파일 생성 성공이 클라이언트 저장 완료를 뜻하지 않는다.
- AdminAccessLog는 로그인 이력이며 개인정보 조회 계측으로 사용할 수 없다. 조회는 목록/상세 성공 요청 1건을 1회로 정의하고, 고유 조회 대상 수와 구분한다. 자동 갱신/백그라운드 요청은 분리해야 한다.
- 기존 excel_download_logs의 확인한 필드에는 conferenceSeq가 없어 학회별 집계 구현 전 신뢰할 수 있는 학회 귀속 필드 및 과거 이력 처리 방식을 설계해야 한다. 불명확한 이력을 선택 학회 데이터로 간주하지 않는다.
- 실제 연동 시 감사 권한을 서버에서 검증하고 개인정보 원문을 통계에 보내지 않는다. 현 화면은 전부 가상 데이터이며 권한/API/DB/수집 기능은 변경하지 않았다.

## 사용자 핵심 기능 상태 및 오류 내역

- `UserFeatureHealthPreview.tsx`에 로그인/회원가입/사전등록/결제/초록제출 5개 기능을 추가했다. 백엔드·API·DB 변경은 없다.
- 기준 시간은 2026-09-13 13:30–14:30 KST. 기능별 성공/시스템 오류/입력·조건 미충족은 서로 배타적인 시도 결과이다. 사전등록 저장과 결제는 별도 단계이고 재시도 및 단계 간 동일 사용자 중복을 포함한다.
- 오류 건수는 오류 내역 예시에서 합산한다. 로그인 2, 회원가입 1, 사전등록 4, 결제 8, 초록 3 = 18건. 상단 서버 오류 18건에 포함된다. 이 예시에서 시스템 오류는 모두 서버 오류 응답을 낸 요청이며 향후 브라우저/네트워크 오류를 수집하면 서버 오류율과 별도 집계해야 한다.
- 결제 응답 지연 8건 중 승인/내부 상태 불일치 2건이 포함된 예시. 합산하지 않으며 결제 실패라고 단정하지 않는다.
- 입력·조건 미충족은 비밀번호 불일치, 중복 가입, 필수값 누락, PG 거절 등을 뜻하며 장애 집계와 분리한다.
- 카드의 오류 보기로 기능 필터를 적용하고 오류 제목에 포커스를 이동한다. 검색어/기능/처리 상태는 조회 또는 Enter로 함께 적용하고 초기화는 전체를 복원한다.
- 오류 목록은 같은 기능/코드의 발생을 묶은 5개 유형 전체이며 최근 발생순이다. 필터 결과의 유형 수와 발생 횟수를 별도 표시한다. 빈 검색 결과를 제공한다.
- 상세는 발생 단계, 사용자 안내, 영향, 권장 조치, 처리 경과, 대표 추적번호로 구성한다. 원본 요청/비밀번호/이메일/결제정보/스택트레이스는 표시하지 않는다.
- 복구 확인은 명시적인 재점검 결과로 표시하며 최근 성공 요청이 있다는 이유만으로 전체 기능 정상으로 판단하지 않는다. 조사 중 상태를 유지한 채 최근 성공 시각도 함께 보여준다.
- 실제 로그 수집 및 처리 상태 저장, 자동 감시/복구 기능은 화면 확정 후 별도 작업이다.
